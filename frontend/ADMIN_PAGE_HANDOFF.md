## 0. Исходный запрос

Пользователь попросил:

> «Продумай страницу для админа сервиса. Пока не реализуй её, только опиши для меня.»

То есть нужен **дизайн-концепт**, а не код. Реализация — следующий шаг,
и начинать её стоит только после ответов на открытые вопросы в §6.

## 1. Проект в двух абзацах

**BarberSearch** — сервис поиска барберов и онлайн-записи. Репозиторий:
`D:\Projects\barbersearch`; рабочая папка текущей сессии — `frontend/`.
Git-корень на уровень выше рабочей папки, поэтому git-команды запускаются
из `frontend/` и находят корень сами.

**Frontend:** React 19.3.1, TypeScript 6.0.3, Vite 8.3.5, Tailwind CSS 4.3.3
(CSS-first, без `tailwind.config`), shadcn/ui на Base UI (`base-nova`),
шрифт Geist Variable. Роутера нет — самодельный History API в
`src/lib/router.ts`. Нет TanStack Query, react-hook-form, zod, тест-раннера
и переключателя тёмной темы. UI-копия русская, идентификаторы английские.

**Backend:** ASP.NET Core (.NET 10), DDD, EF Core + PostgreSQL. Роли:
`Customer`, `Barber`, `Admin`; админские действия закрыты политикой
`AdminOnly`. Аутентификация — HttpOnly-cookie + CSRF-заголовок
`X-CSRF-TOKEN` на каждом изменяющем запросе. Ошибки — ProblemDetails
с расширением `errorCodes`; клиент ветвится по коду, а не по тексту.

## 2. Что уже проверено: факты, на которые опирается дизайн

### 2.1 Frontend

- Маршруты ровно два: `/` (витрина) и `/account` (кабинет клиента).
  `App.tsx` выбирает страницу по точному `pathname`; неизвестный адрес
  показывает витрину.
- `usePathname()` и `navigate()` живут в `src/lib/router.ts`; поиск
  (`?tab=`) и вложенные пути не поддерживаются, но добавляются дешёво.
- Сессия: `SessionProvider` делает `GET /api/auth/me` при монтировании;
  `SessionUser = { id, email, role, barberProfileId, isEmailVerified }`,
  `role` пока обычная строка, не union.
- В кабинете `RoleGate` честно говорит барберу и админу, что их кабинет
  ещё не готов (`src/components/account/account-gates.tsx`).
- Дизайн-система: нейтральные `oklch`-токены в `src/index.css`, `Geist`,
  радиус `0.625rem`, поверхности `ring-1 ring-foreground/10`, контейнер
  `max-w-5xl`, шапка `h-14` sticky. Токены `--warning`, `--success`,
  `--destructive` уже есть и используются в статусах броней.
- UI-кит: `avatar`, `badge`, `button`, `card`, `checkbox`, `dialog`,
  `field`, `input`, `label`, `separator`, `skeleton`. Нет `table`,
  `tabs`, `select`, `dropdown-menu`, `alert-dialog`, `sheet`.
- Вкладки в кабинете сделаны вручную с roving tabindex
  (`src/components/account/booking-list.tsx`) — паттерн можно переиспользовать.

### 2.2 Backend: что админ уже умеет

**Отзывы (пре-модерация):**

- `POST /api/reviews` создаёт отзыв скрытым (`IsPublished = false`),
  рейтинг барбера не меняется.
- `GET /api/reviews/moderation` — очередь скрытых отзывов всех барберов,
  только админ, порядок `created_at ASC, id` (FIFO), курсор.
- `POST /api/reviews/{id}/publication` — опубликовать (пересчёт рейтинга).
- `DELETE /api/reviews/{id}/publication` — скрыть (пересчёт рейтинга).
- `PUT /api/reviews/{id}` технически доступен админу через
  `EnsureCanManage`, но интерфейс этого делать не должен (см. §3.4).
- `ReviewResponse` содержит только `Id`, `BarberProfileId`, `UserId`,
  `BookingId`, `Rating`, `Text`, `IsPublished`, `CreatedAt`, `UpdatedAt`.
  **Имён барбера и клиента нет.** Этот же контракт используется публичным
  списком отзывов, поэтому добавлять туда PII нельзя.

**Барберы:**

- `POST/DELETE /api/barber-profiles/{id}/verification` — подтвердить/снять.
- `PUT /api/barber-profiles/{id}/grade` — грейд.
- `PUT /api/barber-profiles/{id}/rating` — ручной пересчёт.
- `POST/DELETE /api/barber-profiles/{id}/activation` — скрыть/вернуть.
- Публичный `GET /api/barbers` показывает только `IsActive && IsVerified`,
  а `GET /api/barbers/{id}` отдаёт 404 для скрытого/неподтверждённого.
  Значит, список «на проверке» без нового админского чтения не собрать.

**Пользователи:**

- `POST /api/users` — создать (только админ; пароль 12–128).
- `PUT /api/users/{id}/role` — сменить роль (ротирует `SecurityStamp`,
  все сессии пользователя завершаются).
- `POST/DELETE /api/users/{id}/activation` — активировать/заблокировать.
- `POST /api/users/{id}/email-verification`,
  `POST /api/users/{id}/phone-verification` — подтвердить.
- `PUT /api/users/{id}/barber-profile/{barberProfileId}` — привязать профиль.
- **Списка пользователей нет** — ни `GET /api/users`, ни `GET /api/users/{id}`.

**Каталог:**

- Салоны: `POST /api/salons`, `PUT /api/salons/{id}/location`,
  `PUT /api/salons/{id}/contact-info`, `POST/DELETE /api/salons/{id}/activation`.
- Услуги: `POST /api/hair-services`, `PUT /api/hair-services/{id}`,
  `POST/DELETE /api/hair-services/{id}/activation`.
- Специализации: `POST /api/specializations`, `PUT /api/specializations/{id}`,
  `POST/DELETE /api/specializations/{id}/activation`.
- **Ни у одного из трёх справочников нет GET-списка.** При этом в
  репозиториях уже есть `GetPagedAsync` (offset-пагинация, глубина до 10 000).

**Брони:**

- `GET /api/bookings` — админ видит все, может фильтровать по `userId`;
  обычный пользователь — только свои.
- `BookingResponse` содержит идентификаторы, время, цену, статус, заметки.
  Имён клиента/барбера/салона/услуги в ответе нет.
- Админ может отменить чужую бронь и отметить неявку (проходит
  `EnsureIsBarberOfAsync` благодаря `IsAdmin`).

**Аудит:**

- Таблица `audit_log` пишется в той же транзакции, что и изменение
  (`AuditTrail`), с `actorUserId`, действием, типом сущности, id и JSON-payload.
- Аудируются только `User`, `BarberProfile`, `Review` и только свойства
  из allowlist. Логины и «неадминистративные» правки не пишутся.
- **Read-эндпоинта нет.** Правки салонов, услуг и специализаций в журнал
  не попадают — это надо либо принять, либо расширить allowlist.

**Прочее:**

- Лимиты: записи 30/мин, auth 10/мин, анонимные чтения 120/мин.
- Пейджинг: публичные списки — keyset (`nextCursor`), админские — offset
  с ограничением глубины; лимит `pageSize` — 100.
- Enum'ы в JSON — строками (`Grade`, `UserRole`, `ServiceCategory`).
- Грейды: `None`, `Intern`, `JuniorBarber`, `MiddleBarber`, `SeniorBarber`,
  `ArtDirector`, `BarberSchoolTrainer`, `Manager`, `CompetitionBarber`,
  `BrandAmbassador`, `BarbershopOwner`.
- Категории услуг: `Haircut`, `Beard`, `Coloring`, `Styling`,
  `HairTreatment`, `Other`.

### 2.3 Чего не хватает для страницы

| Раздел | Уже есть | Нужно добавить |
|---|---|---|
| Вход | `GET /api/auth/me` | — |
| Очередь отзывов | `GET /api/reviews/moderation`, публикация/скрытие | Отдельный админский DTO с именем барбера, клиентом и визитом |
| Опубликованные отзывы | скрытие | `GET /api/admin/reviews?status=published`, `GET /api/admin/reviews/{id}` |
| Барберы | verify/unverify, grade, rating, activation | `GET /api/admin/barbers`, `GET /api/admin/barbers/{id}` |
| Пользователи | create/role/activation/verification/link | `GET /api/admin/users`, `GET /api/admin/users/{id}` |
| Каталог | create/update/activation | `GET` списков услуг, специализаций, салонов |
| Брони | `GET /api/bookings` | Имена и контекст в ответе; поиск пользователя |
| Журнал | таблица `audit_log` | `GET /api/admin/audit` (read-only) |
| Сводка | — | `GET /api/admin/summary` (опционально, позже) |

**Ключевое правило:** не добавлять PII в общие контракты
(`ReviewResponse`, `BookingResponse`). Для админки — отдельные DTO,
иначе имена и email утекут на публичную витрину.

## 3. Дизайн-концепт

### 3.1 Тезис

Это **не дашборд**, а рабочий стол модератора. Страница открывается на
очереди отзывов — на том, что требует решения сегодня, — а не на графиках.
Разделы «Барберы», «Пользователи», «Каталог», «Брони» и «Журнал» живут
рядом, но подчинены одному сценарию: быстро принять решение и двигаться
дальше.

Почему: единственная ежедневная операция админа — разбор отзывов
(пре-модерация включена). Верификация и каталог — редкие ответственные
действия; роли и блокировки — ещё реже. Поэтому очередь первична,
«сводка» — вторична.

### 3.2 Вход и доступ

- Один маршрут `/admin`, но у разделов свои адреса:
  `/admin/reviews`, `/admin/barbers`, `/admin/users`, `/admin/catalogue`,
  `/admin/bookings`, `/admin/audit`. Перезагрузка и «назад» возвращают
  в тот же раздел и к той же карточке.
- Роль — из `GET /api/auth/me` (`role === 'Admin'`). Клиентская проверка
  только для UX; бэкенд всё равно закрывает действия `AdminOnly`.
- Аноним видит «Вход для администраторов» с обычным `LoginDialog`;
  после входа возвращается на `/admin`.
- `Customer`/`Barber` видит «Раздел доступен только администратору»
  и кнопку «На сайт». Данные не раскрываются.
- Точки входа: пункт «Администрирование» в шапке только для админа;
  на `/account` вместо заглушки «Кабинет администратора ещё не готов» —
  карточка «Вы администратор» с кнопкой «Открыть администрирование»;
  прямой URL.
- На `/admin` маркетинговая шапка урезается: логотип, «На сайт», аккаунт.
  Футер витрины скрыт. Это не отдельное приложение, а режим того же SPA.
- `<title>` — «Отзывы — администрирование BarberSearch». `noindex`
  ставится динамически, но защитой не считается: данные закрыты API.

### 3.3 Каркас

- Ширина `max-w-6xl` вместо `max-w-5xl`: нужны таблицы.
- Слева рейл 13rem, sticky под шапкой; справа контент.
- Сверху контента: `h1` раздела, одна строка пояснения, справа
  «Обновлено в 18:42» и кнопка обновления.
- На мобильном рейл — горизонтальная прокручиваемая лента под заголовком.
  Таблицы превращаются в карточки, деталь — на весь экран с «Назад».
- В рейле только работающие разделы: мёртвых ссылок «скоро» нет.
  Счётчики — только при достоверных данных; выдуманные числа запрещены.

### 3.4 Главный экран: «Отзывы»

**Две вкладки:**

- **«На модерации»** — скрытые отзывы, сначала старые (FIFO, как отдаёт
  бэкенд). Здесь принимается решение.
- **«Опубликованные»** — опубликованные, сначала новые. Здесь можно
  скрыть уже публичный отзыв.

Вторая вкладка принципиальна: без неё нельзя убрать с карточки
оскорбительный отзыв, который уже опубликован. `DELETE .../publication`
есть, списка опубликованных — нет.

**Строка очереди** (~64 px, не карточка):

- оценка цифрой и маленькой звездой;
- «Дмитрий К.» — имя сокращено;
- «ждёт 3 дня»; после 48 часов текст получает `text-warning`,
  но длительность написана словами, поэтому цвет не единственный сигнал;
- тонкая полоса слева у выбранной строки; «непрочитанности» нет —
  её нет в модели.

Сверху подпись «Сначала старые». Внизу «Показать ещё» по курсору.
Общего количества в API нет — «Показано 20», а не «20 из 137».

**Деталь отзыва** — место, где админ читает и решает:

- оценка 48–56 px, `font-medium`, `tabular-nums`, рядом звёзды и «4 из 5»;
- текст `text-lg leading-relaxed max-w-prose`; если текста нет —
  «Клиент поставил оценку без комментария»;
- контекст `dl`: барбер, клиент, визит (услуга, салон, цена, дата
  в поясе салона), когда оставлен отзыв;
- «Сейчас у барбера 4,8, 24 отзыва. После публикации рейтинг
  пересчитается» — последствие видно до нажатия;
- внизу липкая панель: **«Опубликовать»** (primary) и
  **«Пропустить»** (ghost).

«Пропустить» ничего не меняет: отзыв остаётся скрытым, админ идёт
к следующему. Это важно для очереди, где не хочется решать второпях.

**Публикация и отмена:**

- кнопка блокируется, текст «Публикуем…», вторая кнопка тоже;
- успех: строка уходит, выбирается следующий отзыв, в `role="status"`
  появляется «Отзыв опубликован. Рейтинг барбера пересчитан» и кнопка
  **«Скрыть отзыв»** — обратимость на месте;
- ошибка: «Не удалось опубликовать отзыв. Попробуйте ещё раз»,
  без английского `detail` и кода HTTP;
- если отзыв уже разобрал другой админ, публикация идемпотентна;
  после ответа список обновляется и показывает «Этот отзыв уже не в очереди».

**Вкладка «Опубликованные»:** тот же split-view, но primary —
**«Скрыть отзыв»** (destructive-outline), с подтверждением:

> Отзыв исчезнет с карточки барбера, рейтинг пересчитается.
> Вернуть отзыв можно в любой момент.

Скрытие возвращает отзыв в очередь — это и есть отмена.

**Чего здесь сознательно нет:**

- **Массовой публикации.** Нельзя выделить 20 отзывов и опубликовать:
  рейтинг — публичное обещание, каждый отзыв читается отдельно.
- **Редактирования текста клиента.** Технически `PUT /api/reviews/{id}`
  доступен админу, но интерфейс этого не предлагает: чужие слова
  не переписываем. Нарушение правил → «Скрыть».
- **Автоматических «токсичных» флагов.** Решение за человеком.

Рядом с заголовком — «Правила модерации» с коротким диалогом: отзыв
о визите, без оскорблений, рекламы, ссылок и чужих персональных данных.
Это снижает разброс решений между админами.

**Адрес и состояние:**

- выбранный отзыв — в адресе: `/admin/reviews/{id}`; перезагрузка
  и «назад» не теряют карточку;
- если отзыв уже не в очереди — «Этот отзыв уже разобрали» и выбор первого;
- мобильный сценарий: список → деталь на весь экран с «Назад»;
  фокус возвращается на строку, с которой ушли.

### 3.5 «Барберы»

Задача — подтвердить профиль, присвоить грейд, убрать из поиска.

- Список с поиском «Имя или email» и фильтром: «Все», «На проверке»,
  «Скрытые».
- Строка: аватар с инициалами, имя, email, грейд, рейтинг и число отзывов,
  бейдж «Подтверждён / На проверке / Скрыт».
- Клик открывает боковую панель (Sheet) с блоком **«Готовность профиля»**:
  профиль заполнен, услуги (N), салон (N), расписание (N дней), фото (N),
  email подтверждён. Это чек-лист, а не блокировка: подтвердить можно
  и с минусами, но админ видит, чего не хватает.
- Действия: «Подтвердить», «Снять подтверждение», «Изменить грейд»,
  «Скрыть из поиска», «Открыть публичную карточку» (только если виден).
- Копия подтверждения: «Профиль появится в поиске и станет доступен
  для записи. Отменить это можно в любой момент».
- Грейды по-русски: «Без грейда», «Стажёр», «Младший барбер», «Барбер»,
  «Старший барбер», «Арт-директор», «Тренер школы», «Управляющий»,
  «Соревновательный барбер», «Амбассадор бренда», «Владелец барбершопа».

### 3.6 «Пользователи»

Задача — роли, доступ, подтверждения.

- Поиск по имени/email, фильтры по роли и статусу.
- Таблица: пользователь, роль, статус, последний вход, создан.
  На мобильном — карточки.
- Деталь: контакты, роль, статус, профиль барбера, кнопки «Подтвердить
  email», «Подтвердить телефон», «Привязать профиль барбера»,
  «Заблокировать доступ».
- Смена роли и блокировка требуют подтверждения с последствием:
  «Смена роли завершит все текущие сессии пользователя»,
  «Пользователь потеряет доступ, все его сессии завершатся.
  Записи и отзывы сохранятся».
- Нельзя менять роль себе и блокировать себя. Для последнего админа
  нужна отдельная защита — сейчас её нет на бэкенде, и это риск:
  единственный админ может снять с себя роль и закрыть сервис.
- «Создать пользователя»: email, имя, фамилия, роль, временный пароль
  (12–128, кнопка «Сгенерировать»). После создания — панель
  «Пользователь создан. Передайте пароль безопасным каналом —
  больше он не покажется»: отправки писем в системе нет.

### 3.7 «Каталог»

Три вкладки: «Услуги», «Специализации», «Салоны». Везде таблица
и диалог создания/правки.

- **Услуги:** название, категория («Стрижка», «Борода», «Окрашивание»,
  «Укладка», «Уход за волосами», «Другое»), длительность по умолчанию,
  статус. На правке категория read-only с подсказкой «Категория
  не меняется после создания» — это правило бэкенда.
- **Специализации:** название, описание, статус; переименование
  и включение/выключение.
- **Салоны:** название, город, адрес, часовой пояс, контакты, координаты,
  статус. Часовой пояс — поисковый select из IANA-зон, а не свободный
  текст: опечатка ломает расчёт слотов.
- Выключение объясняет последствие: «Услуга исчезнет из поиска
  и карточек, но останется в истории записей»; «Салон исчезнет
  из поиска. Барберы, которые работают только здесь, могут перестать
  показываться».
- Удаления нет нигде: только «Выключить» / «Включить».

### 3.8 «Брони»

Поддержка, а не ежедневная работа: поиск по email клиента или ID брони,
фильтр по статусу, таблица и деталь с временем в поясе салона.
Действия — «Отменить бронь» и «Отметить неявку» (после начала визита),
с подтверждением. Ответ `GET /api/bookings` содержит только
идентификаторы, поэтому имена без нового админского контракта не показать.

### 3.9 «Журнал»

Read-only история: когда, кто, что изменил, у какой сущности, diff полей.
Строка раскрывается: `role: Customer → Admin`,
`isPublished: false → true`. Фильтры по типу сущности, автору и дате.
«Записи не редактируются» — часть доверия к журналу.

Таблица `audit_log` уже пишется, но read-эндпоинта нет. Аудит покрывает
только `User`, `BarberProfile`, `Review`, поэтому правки каталога
в журнал не попадут. Либо расширяем allowlist, либо честно говорим,
что каталог не аудируется.

### 3.10 «Сводка» — позже

Не стартовая. Когда появятся агрегаты, это может быть скромный экран
«Требует внимания»: отзывы на модерации и самый старый из них, барберы
без подтверждения, выключенные салоны. Без KPI-карточек и графиков.
Стартовая страница — всё равно очередь.

### 3.11 Визуальный язык

Остаёмся внутри существующей системы: Geist, нейтральные токены,
`ring-1 ring-foreground/10`, радиусы из `--radius`. Новых шрифтов
и палитры не вводим — это осознанное решение.

- **Один акцент:** крупная цифра оценки и текст отзыва в детали.
  Всё остальное — служебный интерфейс 12–14 px.
- **Плотность:** рейл 13rem, строка очереди 64 px, между блоками 24 px.
  Админка собраннее витрины, но не таблица ради таблицы.
- **Статусы:** точка + текст, цвета из `--warning`, `--success`,
  `--destructive`. Цвет никогда не единственный носитель смысла.
- **Поверхности:** тонкие разделители и ring вместо теней и градиентов.
  Никаких «карточек на всё».
- **Движение:** 120–160 ms; после публикации строка уходит, деталь
  сменяется; при `prefers-reduced-motion` — без анимации.
- **Пустые состояния:** иконка в muted-круге и одно предложение,
  как в кабинете клиента. Без иллюстраций.

Из UI-кита понадобятся `table`, `select`, `dropdown-menu`,
`alert-dialog`, `sheet` — добавить через shadcn CLI. Вкладки можно
не тянуть: в `booking-list.tsx` уже есть аккуратный ручной паттерн
с roving tabindex.

### 3.12 Состояния и доступность

- Загрузка: скелетон повторяет силуэт (рейл + строки + деталь),
  `aria-busy`, `sr-only`-статус.
- Пусто: «Очередь пуста. Все отзывы проверены. Новые появятся здесь,
  как только клиенты их оставят» и «Обновить».
- Ошибка: причина и «Повторить», без `detail` и кода ответа.
- `401` → гейт входа с возвратом в очередь; `403` → «Раздел доступен
  только администратору»; `429` → «Слишком много действий подряд.
  Подождите минуту».
- Один `h1` на раздел, `h2` у панелей. Рейл —
  `<nav aria-label="Разделы администрирования">`, активный пункт
  `aria-current="page"`.
- Список очереди — кнопки с `aria-current` и roving tabindex:
  стрелки ходят по строкам, Tab не растягивается на сотню элементов.
  Выбранная деталь связана `aria-controls`.
- После публикации и скрытия — `role="status"`; после удаления строки
  фокус переходит на следующую, а не в `<body>`.
- На мобильном деталь — отдельный экран; «Назад» возвращает фокус
  на строку.
- Контраст `warning` на светлом фоне проверить отдельно; если
  не дотягивает до AA, оставить цветную точку, а текст — `foreground`.
- 320 px: без горизонтальной прокрутки, действия не меньше 44 px.

## 4. Правила и риски

1. **Последний админ.** Сейчас бэкенд не запрещает снять роль
   с последнего администратора. Это надо закрыть либо правилом
   в Application, либо хотя бы запретом на себя в UI.
2. **Смена роли и блокировка** меняют `SecurityStamp` и завершают все
   сессии пользователя. Об этом надо писать в подтверждении.
3. **Аудит каталога** не ведётся. Если каталог редактируется в админке,
   стоит расширить allowlist `AuditTrail`.
4. **Лимит записи 30/мин.** Массовых операций нет; кнопки блокируются
   на время запроса. Это причина не делать bulk-публикацию.
5. **PII.** Email клиента виден админу, но не попадает в URL,
   localStorage или логи. Телефон без необходимости не показываем.
6. **Никаких удалений.** В домене их нет; интерфейс использует
   «Скрыть», «Выключить», «Заблокировать».
7. **Два админа одновременно.** Публикация идемпотентна, но список
   может устареть; после каждого действия — тихое обновление очереди.
8. **Не рисовать общее количество очереди**, пока его нет в API.
   Лучше «Показано 20» и «Показать ещё», чем выдуманное «137».
9. **Не добавлять PII в общие контракты.** Отдельные админские DTO.

## 5. Этапы

1. **Каркас + «Отзывы».** Маршрут `/admin`, гейт по роли, рейл, очередь,
   деталь, публикация/скрытие, вкладка опубликованных, пустые
   и ошибочные состояния. Это уже полноценная ежедневная работа.
2. **«Барберы».** Список на проверке, деталь, чек-лист готовности,
   подтверждение и грейд.
3. **«Пользователи».** Список, роли, блокировка, подтверждения,
   создание с одноразовым паролем.
4. **«Каталог».** Услуги, специализации, салоны; формы и выключение.
5. **«Журнал».** Read-only история и diff.
6. **«Брони» и «Сводка».** Поддержка и агрегаты, когда появятся контракты.

Порядок продиктован риском: отзывы обратимы и ежедневны, барберы влияют
на предложение, пользователи — самые чувствительные, каталог — редкий,
журнал нужен для доверия ко всему перечисленному.

## 6. Открытые вопросы (решить до кода)

1. **Стартовый экран:** очередь отзывов (рекомендация) или «Сводка»?
2. **PII:** показываем ли админу email клиента полностью?
   Рекомендация — да, без него модерация и поддержка слепые.
3. **Статус «отклонён» с причиной:** добавляем в домен или обходимся
   парой «опубликовать / оставить скрытым»? Рекомендация — не добавлять
   состояние без продуктовой необходимости.
4. **Последний администратор:** правило на бэкенде или только прячем
   кнопку в UI? Рекомендация — правило на бэкенде.
5. **Один админ или команда?** От этого зависит важность журнала,
   одновременной работы и отображения автора действия.
6. **Мобильный сценарий:** админ работает с телефона или только
   с десктопа? Дизайн предполагает desktop-first с работоспособной
   мобильной модерацией.
